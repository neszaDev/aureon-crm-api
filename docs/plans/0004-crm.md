# Plan 0004: Aureon CRM on both boilerplates

## Context

The owner asked (2026-10-17) for a complete, production-quality multi-tenant CRM template built
by extending this API and [nextjs-boilerplate](https://github.com/neszaDev/nextjs-boilerplate),
to use as a portfolio project and a template to sell. The specification is in
[docs/crm/](../crm/README.md); this plan is how it gets built and verified.

## Decisions

| Question | Decision | Why |
|---|---|---|
| Where does it live? | Branch `feat/crm` in both repos (from `dev`). Not merged to `dev`/`main` without the owner's approval | Keeps the boilerplates generic; CRM code is also in its own packages (`crm/`, `workspace/`) |
| Tenant model | Workspace id in the URL path; membership checked per request from the database; Hibernate `@TenantId` filter; composite foreign keys | A user can be in several workspaces; isolation is enforced in three independent layers ([permissions.md](../crm/permissions.md)) |
| Tokens | Unchanged: no workspace claim in the JWT | Roles change without re-issuing tokens; the auth module stays the boilerplate's |
| Joining | Invitation links only (token hashed like refresh tokens, 7 days, email must match). Self-service sign-up stays, and can be turned off (`REGISTRATION_ENABLED=false`) for invite-only deployments | No email service in a zero-cost template; the link is shared by the admin |
| Records | Archive and restore instead of delete; activities may be deleted | History and links survive; no cascading business-data loss |
| Money | `NUMERIC(15,2)` + ISO currency per deal, JSON strings, totals per currency, no conversion | No floating point; conversion needs a rate source (non-goal) |
| Sales rep scope | Reads everything in the workspace; edits only their own records | Small teams collaborate; edit rights separate the roles |
| Updates | `PUT` with all editable fields and `version`; state changes as `POST` actions | Explicit stale-write detection (409); one place per state rule |
| Frontend routes | The CRM is the signed-in home: `/app` (workspace picker) and `/app/{workspaceId}/...`. The boilerplate pages stay under `/dashboard` | The template's product is the CRM; existing features keep working |
| Look | A new, original design system for the CRM ("Aureon"), with light and dark themes; `DESIGN.md` is replaced on the branch | The Marksheet report-card look was a placeholder for the test-results demo |
| Languages | English (default), French (existing) and Thai, every key in every locale | The i18n check requires complete locales |
| Dependencies | None new in either repo (dnd-kit, TanStack Table, recharts, react-hook-form, zod, sonner are already installed) | |

## Phases and gates

Each slice is implemented, tested and reviewed before the next starts. A gate passes only on
commands that were actually run.

| Phase | Backend slice | Frontend slice | Gate |
|---|---|---|---|
| 1 Foundation | **B1**: display name, change password, registration flag; workspaces, members, roles, `WorkspaceContext` + `@TenantId`, invitations, audit trail, pipeline stages, lead sources; cross-workspace test harness | **F1**: Aureon design system + `DESIGN.md`, theme toggle, CRM shell, workspace picker/creation, invitation page, settings (workspace, members, invitations, roles, pipeline, sources, profile, password), proxy and redirects, Thai locale | `make verify` green in both; `make e2e` for auth/workspace flows |
| 2 Core | **B2**: companies, contacts, leads (status, conversion), deals (board, move, history), tasks (actions, reminders), activities; search, filters, sorting, paging, duplicates, archive/restore | **F2**: list and detail pages for every record, forms, convert dialog, kanban with drag and drop plus a keyboard "move to" menu, list view, task views, timelines | same, plus e2e of each flow |
| 3 Insights | **B3**: dashboard, reports, CSV export, audit read, demo data seeder | **F3**: dashboard, reports with charts, export buttons, reminders, audit page, landing copy | same |
| 4 Quality | security review against [permissions.md](../crm/permissions.md); clean-database migration run; full suites | the 10-step e2e workflow, a11y check, responsive review | all suites green, no open critical finding |
| 5 Delivery | docs: setup, architecture, API, security notes, deployment checklist, feature matrix, limitations | user guide, README | final report |

## Working method

- One technical lead (the main agent) owns this plan, the contract in `docs/crm/` and integration.
  Implementation and review are delegated per slice to sub-agents with a written brief; their
  results are checked by running the suites, not by reading their reports.
- The development Mac has 8 GB of RAM, so builds and test suites run **one at a time** (backend
  `./mvnw verify` and frontend `make verify`/e2e never in parallel; e2e with `--workers=1`).
  Editing in parallel is fine; verifying is serial.
- The backend is worked on in a separate worktree, so the IDE does not race Maven and the main
  checkout's untouched `mvnw.cmd` stays out of every commit.
- Local CRM stack uses its own ports (API `8081`, Postgres `5434`), because another project uses
  `8080`/`5433` on this machine.
- Frontend CI's e2e job runs against the published backend image, which has no CRM endpoints until
  the backend branch is released. CRM e2e therefore runs locally against this branch; that is
  reported as an environment limitation, not skipped silently.

## Risks

- **Hibernate tenant filter and load by id.** If `find()` were not filtered in this Hibernate
  version, the composite keys and an explicit workspace check in the shared loader cover it; the
  cross-workspace tests decide.
- **Memory.** Long suites on 8 GB; mitigated by running them serially.
- **Translations.** Thai and French strings are written by the agent, not a native speaker.
